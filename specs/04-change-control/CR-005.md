## BUG-001 — Cart Merge on Login Not Working (REQ-USR-003)

### Observed Behaviour
After logging in, items in the guest cart are not merged into the
server-side cart. The server cart appears empty immediately after login.

### Root Cause Analysis
In `LoginPage.tsx` the current order is:
```
1. login(authUser)        ← sets isAuthenticated = true
2. await mergeCart()      ← fires AFTER isAuthenticated flips
```

`login()` calls `setUser(authUser)` which triggers the `CartContext`
`useEffect([isAuthenticated])` to fire `refreshServerCart()`. This reload
races with the `mergeCart()` POST — the cart may refresh before the merge
completes, showing the pre-merge (empty) server cart.

Additionally, `login()` in `AuthContext` relies on `useEffect` to call
`setToken()` — this is asynchronous (effect runs after render). So when
`mergeCart()` fires immediately after `login()`, the JWT may not yet be
in `localStorage`, causing the merge API call to fire without auth and
receive a 401.

### Proposed Fix
In `LoginPage.tsx`, restructure the post-login sequence:
1. Call `setToken(res.token)` directly (synchronous) — JWT immediately
   available in localStorage.
2. Call `await mergeCart()` — merge fires with valid JWT, guest cart
   still intact, `isAuthenticated` still false so no race.
3. Call `login(authUser)` — flips auth state, CartContext refreshes an
   already-merged server cart.
4. Navigate to destination.

Also update `AuthContext.login()` to call `setToken()` synchronously
inside the function body (not only in the `useEffect`) so the token is
guaranteed to be present before the function returns.

### Affected Requirement
REQ-USR-003 AC1, AC2

### Acceptance Criteria
- AC1: After login with guest cart items, those items appear in the server cart.
- AC2: The localStorage guest cart key is empty/cleared after merge.
- AC3: If the guest cart was empty, no merge API call is made.
- AC4: The server cart displayed immediately after login reflects the merged state.

## BUG-002 — Pagination "Next" Button Shows No Books (REQ-CAT-001, REQ-CAT-002, REQ-CAT-003)

### Observed Behaviour
On the Home page, clicking "Next →" loads page 2 but shows "No books found."
Category and publisher filters also do not work correctly.

### Root Cause Analysis

**Sub-issue 2a — Page field name mismatch:**
Spring's `Page<T>` serialises the current page number as `"number"` (not
`"page"`). The frontend `PagedResponse<T>` interface maps this field as
`page`. So `data.page` is always `undefined`:
- `data.page - 1` = `NaN` → backend defaults to page 0 (first page again)
- `data.page >= data.totalPages - 1` = `false` always → Next never disables
- `data.page === 0` = `false` always → Prev never disables

**Sub-issue 2b — Category/publisher filter by name vs ID:**
`BookController.browse()` accepts `categoryId` (Long) and `publisherId`
(Long). The frontend sends `category=Fiction` (name string) and
`publisher=Penguin` (name string). The backend ignores these unknown
params, returning all books unfiltered. The spec (REQ-CAT-002 AC1) states
`GET /api/books?category={name}` — name-based filtering is the requirement.

### Proposed Fix

**2a:** Add a custom `PagedResponseDTO` wrapper in the backend that
serialises Spring's `Page<T>` with an explicit `page` field (matching
the frontend interface). Update `BookController.browse()` to return this
wrapper instead of `Page<T>` directly.

**2b:** Add `category` (String name) and `publisher` (String name)
parameters to `BookController.browse()` and `BookFilterParams`. Update
`BookRepository.findFiltered()` JPQL query to accept name-based filtering
via JOIN on category/publisher name when the name param is present.

### Affected Requirements
REQ-CAT-001 AC1, REQ-CAT-002 AC1, REQ-CAT-003 AC1

### Acceptance Criteria
- AC1: Clicking "Next →" on page 1 loads page 2 with correct books.
- AC2: "← Prev" returns to the correct previous page.
- AC3: Prev is disabled on page 1; Next is disabled on the last page.
- AC4: `GET /api/books?category=Fiction` returns only Fiction books.
- AC5: `GET /api/books?publisher=Penguin` returns only Penguin books.
- AC6: Category + publisher name filters combined with pagination work correctly.

## BUG-003 — Out-of-Stock Books Appear in Recommendations (REQ-REC-001)

### Observed Behaviour
The recommendation strip shows books with `stockQuantity = 0` (out of stock).
Clicking "Add to Cart" on an out-of-stock recommendation fails.

### Root Cause Analysis
`RecommendationService.findCandidatesExcluding()` fetches all books not
in the purchased set, including out-of-stock ones. There is no stock
filter in the candidate query or scoring step.

REQ-REC-001 is silent on stock status — this is a spec gap. Recommending
unavailable books creates a broken user experience and violates the spirit
of REQ-CAT-006 (availability display).

### Proposed Fix
In `RecommendationService.getRecommendations()`, filter the candidate list
to only include `stockQuantity > 0` books before scoring. One-line fix.

### Affected Requirement
REQ-REC-001 (spec gap — clarification added)

### Spec Clarification Added
REQ-REC-001 is amended to add:
> AC5: Only in-stock books (`stockQuantity > 0`) appear in recommendations.

### Acceptance Criteria
- AC1: No out-of-stock book appears in the recommendation strip.
- AC2: In-stock recommended books continue to appear correctly.
- AC3: If all candidates are out of stock, empty list is returned gracefully.

## BUG-004 — Search Page Crashes with TypeError (REQ-SRC-001)

### Observed Behaviour
Navigating to `/search?q=<any term>` throws:
```
TypeError: Cannot read properties of undefined (reading 'length')
at BookGrid (BookGrid.tsx:17)
```

### Root Cause Analysis
`GET /api/books/search` returns `List<BookSummaryDTO>` — a plain JSON
array `[...]`. `SearchPage` stores this in `useState<PagedResponse<BookSummary>>`
and passes it to `<BookGrid>` which reads `data.content.length`. Since the
response is a plain array (not an object with a `content` field),
`data.content` is `undefined` → `TypeError`.

### Proposed Fix (frontend only — no backend change needed)
In `SearchPage.tsx`, when the search endpoint returns a plain array,
wrap it in a synthetic `PagedResponse` object:
```ts
{ content: result, page: 0, size: result.length,
  totalElements: result.length, totalPages: 1 }
```
This makes `BookGrid` receive the expected shape. `totalPages: 1` suppresses
pagination controls (search returns ≤ 50 results — pagination not required).

### Affected Requirement
REQ-SRC-001 AC1, AC4

### Acceptance Criteria
- AC1: Searching for any term shows results without a TypeError.
- AC2: Search results render as a book grid.
- AC3: No pagination controls are shown for search results.
- AC4: Searching for a term with no matches shows "No books found."

## REQ-NEW-001 — Guest Cart Page Access (New Functional Requirement)

### Request
A guest user should be able to navigate to `/cart` and see the items they
have added to their browser-local (localStorage) cart. Currently `/cart`
is wrapped in `<ProtectedRoute>` which redirects unauthenticated users to
the login page.

### Analysis
The spec (REQ-USR-002) states guest cart is stored in localStorage. The
spec (REQ-CRT-004) says "covered by REQ-USR-002". Neither explicitly
requires the `/cart` route to be gated behind authentication.

The current `ProtectedRoute` on `/cart` blocks this. Removing the guard
on `/cart` allows guests to view their localStorage cart. Checkout must
remain protected (REQ-USR-001 AC2).

The `CartPage` already has a dual render path:
- Authenticated → server cart via API
- Guest → `guestItems` from `CartContext`

The only change needed is to remove `<ProtectedRoute>` from the `/cart`
route in `router.tsx`.

### New Requirement
REQ-NEW-001: A guest user may navigate to `/cart` and view the items
stored in their browser's localStorage cart. They may not proceed to
checkout from the cart without logging in.

### Acceptance Criteria
- AC1: A guest user can navigate to `/cart` without being redirected to login.
- AC2: The cart page shows the guest's localStorage items with titles, prices, and quantities.
- AC3: Guest cart quantity controls (add/remove) work on the cart page.
- AC4: "Proceed to checkout" on the guest cart redirects to `/login` (ProtectedRoute remains on `/checkout`).
- AC5: After login from the cart page, guest items are merged and the server cart is shown.

## REQ-NEW-002 — Clear User Data on Logout (New Functional Requirement)

### Request
When an authenticated user clicks Logout, all their personal data must
be cleared from the browser: JWT token, user profile, and server cart
state. Currently `logout()` in `AuthContext` calls `setUser(null)` which
triggers a `useEffect` to call `clearToken()` and
`localStorage.removeItem(USER_KEY)`. This is mostly correct but:

1. `CartContext.serverCart` state is cleared reactively when
   `isAuthenticated` becomes false — this is correct.
2. However, any other user-specific localStorage keys should also be
   cleared explicitly on logout for completeness and security.
3. The current `logout()` does not explicitly clear the server cart from
   memory synchronously — it relies on the `useEffect` in `CartContext`.

### Proposed Fix
Update `AuthContext.logout()` to synchronously:
1. Call `clearToken()` — removes JWT from localStorage immediately.
2. Call `localStorage.removeItem(USER_KEY)` — removes stored user profile.
3. Call `setUser(null)` — triggers re-render, `CartContext` clears server cart.

This makes the logout atomic and not dependent on effect ordering.
No server-side session invalidation is needed (stateless JWT).

### New Requirement
REQ-NEW-002: On logout, all user-specific data (JWT, user profile,
server cart state) is synchronously cleared from the browser before
navigating away.

### Acceptance Criteria
- AC1: After logout, `localStorage` contains no JWT token key.
- AC2: After logout, `localStorage` contains no user profile key.
- AC3: After logout, the cart badge shows the guest cart count (0 if empty).
- AC4: After logout, navigating to `/profile` or `/orders` redirects to login.
- AC5: After logout and back to login, a fresh login works correctly.

## REQ-NEW-003 — Redesigned Theme and Decorated Home Page (New UX Requirement)

### Request
Change the visual theme of the entire application and decorate the home
page following UI/UX design principles.

### Current State
The application uses a plain white/grey theme (`--color-bg: #ffffff`,
`--color-accent: #3b82d4`) with no hero section, no visual hierarchy on
the home page, and minimal decoration throughout.

### Design Specification

#### Colour Palette (warm book/library theme)
```
--color-bg:        #faf7f2    (warm off-white — paper feel)
--color-surface:   #f0ebe3    (warm light surface)
--color-border:    #ddd5c8    (warm border)
--color-text:      #2c2416    (rich dark brown — readable)
--color-muted:     #7a6a58    (warm muted brown)
--color-accent:    #c1440e    (terracotta / burnt orange — warm CTA)
--color-accent-hover: #a33a0c (darker on hover)
--color-secondary: #2c5f8a    (deep teal — secondary actions)
--color-success:   #2d6a4f    (forest green)
--color-danger:    #b91c1c    (deep red)
--color-gold:      #d4a017    (for gift points / star accents)
```

#### Typography
- Headings: `Georgia, "Times New Roman", serif` — classic book aesthetic
- Body: `-apple-system, "Segoe UI", system-ui, sans-serif` — readable UI
- Navbar brand: serif, larger, letter-spaced

#### Navbar Redesign
- Dark background: `--color-text` (#2c2416) with white text
- Brand name styled as a bookstore logo (serif, larger)
- Search bar with rounded pill shape
- Cart icon with accent-coloured badge
- User menu with subtle dropdown feel

#### Home Page — Hero Section (new)
A full-width hero banner above the catalogue with:
- Headline: "Discover Your Next Great Read"
- Subheadline: "113 books across 8 categories — Fiction, Science, History & more"
- A "Browse All Books" CTA button
- Warm gradient background (terracotta to deep brown)

#### Home Page — Category Chips (new)
A horizontal scrollable row of category pills below the hero, allowing
one-click category filtering without using the sidebar.

#### Book Cards — Warmer Style
- Warm border, subtle shadow on hover
- Price in accent colour
- Category badge styled with warm tones

#### General
- Rounded corners increased: `--radius: 8px`
- Slightly more padding and breathing room
- Footer added: "© 2026 E-Bookstore. Built with Spring Boot & React."

### Affected Requirements
No functional requirements change. This is a pure UI/UX enhancement.

### Acceptance Criteria
- AC1: The warm book-themed colour palette is applied globally.
- AC2: The navbar uses the dark background with white text.
- AC3: The home page has a hero section with headline, subheadline, and CTA.
- AC4: Category chips appear below the hero for one-click filtering.
- AC5: Book cards use the updated warm style.
- AC6: All existing pages (login, cart, checkout, orders, profile) use the new theme consistently.
- AC7: No functional regressions — all existing features continue to work.
- AC8: A footer with copyright text is present on all pages.
